# SOC Lab Troubleshooting Guide

When building a multi-virtual-machine security monitoring lab, you may encounter networking, service, or ingestion issues. This guide lists common symptoms, root causes, and verified solutions.

---

## 1. Wazuh Agent Shows "Never Connected" or "Disconnected"

### Symptoms
- In the Wazuh Dashboard under **Agents**, the Windows endpoint displays status **Disconnected** or **Never connected**.
- Alerts from the Windows VM are not visible in the dashboard.

### Diagnostic Steps
1. **Check Windows Agent Log**:
   In PowerShell on Windows:
   ```powershell
   Get-Content "C:\Program Files (x86)\ossec-agent\ossec.log" -Tail 30
   ```
   *Look for errors like:* `Cannot connect to server 192.168.56.10:1514` or `Invalid key`.

2. **Test Port Reachability from Windows**:
   ```powershell
   Test-NetConnection -ComputerName 192.168.56.10 -Port 1514
   ```
   If `TcpTestSucceeded` is `False`, the connection is blocked.

3. **Check Ubuntu Server Services and Firewall**:
   In Ubuntu terminal:
   ```bash
   # Confirm manager daemon is listening on TCP 1514
   sudo ss -tulpn | grep 1514

   # Check UFW firewall status
   sudo ufw status
   ```

### Solutions
- **Firewall Block**: Run `sudo ufw allow 1514/tcp && sudo ufw allow 1515/tcp` on Ubuntu.
- **Incorrect Manager IP**: Open `C:\Program Files (x86)\ossec-agent\ossec.conf` on Windows. Look inside the `<client><server>` block and confirm `<address>192.168.56.10</address>` matches your Ubuntu Host-Only IP.
- **Restart Agent Service**:
  ```powershell
  Restart-Service WazuhSvc
  ```

## 2. Windows Drops Ping Requests (ICMP Timeout)

### Symptoms
- Pinging the Windows VM from Ubuntu (`ping 192.168.56.20`) yields `Request timed out` or `Destination Host Unreachable`.

### Root Cause
By default, Windows Defender Firewall blocks all inbound ICMPv4 Echo Requests (ping) on public and private profiles.

### Solution
Allow ICMP echo requests through Windows Firewall via PowerShell (run as Administrator on Windows):
```powershell
New-NetFirewallRule -DisplayName "Allow Inbound ICMPv4 Ping" -Direction Inbound -Protocol ICMPv4 -IcmpType 8 -Action Allow
```
Pinging `192.168.56.20` should now succeed.

## 3. Sysmon Telemetry Not Appearing in Wazuh

### Symptoms
- Standard Windows logon events appear in Wazuh, but process creation events (Sysmon Event ID 1) or network connections (Sysmon Event ID 3) are missing.

### Diagnostic Steps
1. **Verify Sysmon is Active on Windows**:
   ```powershell
   Get-Service Sysmon64
   ```
   If stopped, run: `Start-Service Sysmon64`.
2. **Verify Sysmon is Generating Events Locally**:
   Open Windows Event Viewer (`eventvwr.msc`) -> **Applications and Services Logs** -> **Microsoft** -> **Windows** -> **Sysmon** -> **Operational**. Confirm new events are arriving when applications are launched.
3. **Verify `ossec.conf` Configuration**:
   Ensure the following block exists inside `C:\Program Files (x86)\ossec-agent\ossec.conf`:
   ```xml
   <localfile>
     <location>Microsoft-Windows-Sysmon/Operational</location>
     <log_format>eventchannel</log_format>
   </localfile>
   ```

### Solution
If you modified `ossec.conf`, you **must** restart the agent service for changes to take effect:
```powershell
Restart-Service WazuhSvc
```

## 4. Ubuntu Server Running Out of RAM (OOM Killer)

### Symptoms
- Wazuh Indexer stops unexpectedly.
- Web dashboard displays `502 Bad Gateway` or `Server not responding`.
- System log mentions `Out of memory: Killed process ... (java/opensearch)`.

### Root Cause
Wazuh Indexer runs on the JVM and requires substantial heap memory. If the Ubuntu VM has less than 4 GB RAM allocated or lacks swap space, the Linux kernel terminates high-memory processes.

### Diagnostic Commands
```bash
# Check memory and swap usage
free -h

# Check kernel logs for Out-Of-Memory events
sudo dmesg -T | grep -i oom
```

### Solution: Create a 4 GB Swap File
Add a swap file on Ubuntu to prevent out-of-memory crashes:
```bash
sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

# Make permanent across reboots
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# Restart Wazuh services
sudo systemctl restart wazuh-indexer
sudo systemctl restart wazuh-manager
sudo systemctl restart wazuh-dashboard
```

## 5. Wazuh Indexer Disk Space Watermark Error

### Symptoms
- Wazuh Indexer logs display: `disk watermark [flood_stage] exceeded ... indices will be read-only`.
- Alerts are generated by the manager but do not appear in the dashboard.

### Root Cause
OpenSearch protects itself by setting indices to read-only when available disk space drops below 95% (or 85% for high watermark).

### Solution
1. Check disk utilization:
   ```bash
   df -h /
   ```
2. Clean package caches and old logs:
   ```bash
   sudo apt clean
   sudo journalctl --vacuum-size=200M
   ```
3. Expand the VirtualBox virtual disk size if necessary.

## 6. Self-Signed Certificate Warnings in Browser

### Symptoms
- Browsing to `https://192.168.56.10` shows a red security alert screen stating *"Your connection is not private"*.

### Explanation & Resolution
Wazuh creates a local Root Certificate Authority (CA) during installation to encrypt internal node-to-node and dashboard-to-user traffic without requiring external certificate authorities (such as Let's Encrypt).
- **Chrome / Edge**: Click **Advanced** -> **Proceed to 192.168.56.10 (unsafe)**.
- **Firefox**: Click **Advanced** -> **Accept the Risk and Continue**.
- *This is expected behavior in an isolated local lab environment.*
